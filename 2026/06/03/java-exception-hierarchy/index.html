Java 异常体系与最佳实践

发表于2026-06-03|更新于2026-06-02
|阅读量:

异常是 Java 错误处理的核心机制。理清 异常层次、分类与处理边界，能写出更易维护、可排查的代码。

1. 类层次结构

  • Error：程序通常无法恢复，如 OOM，应修复资源或配置而非 catch 后忽略。
  • Checked Exception：编译期必须处理（try-catch 或 throws）。
  • RuntimeException：编程错误，编译器不强制处理。

2. 处理原则（阿里巴巴等规范共识）

  1. 不要捕获后什么都不做（空 catch），至少打日志。
  2. 不要用异常做流程控制，异常应真正「异常」。
  3. catch 要具体，避免 catch (Exception e) 吞掉所有问题；必要时先 catch 子类。
  4. finally 中不要 return，以免掩盖 try 中的 return 或异常。
  5. JDK 7+ 使用 try-with-resources 自动关闭资源：

3. 受检 vs 非受检如何选择？

类型 何时使用
Checked 调用方 能够且应该 合理恢复，如文件不存在重试、网络超时切换
Unchecked 编程错误、参数非法、业务规则违反（常用自定义 RuntimeException）

现代框架（Spring 等）倾向将业务异常定为 RuntimeException，避免层层 throws 污染签名。

4. 自定义异常示例

保留 cause 便于链式排查：new BusinessException("下单失败", sqlException)。

5. try-catch-finally 执行顺序

  • 有 return 时：先执行 finally，再执行 return（finally 修改 return 基本类型值不影响已保存的返回值）。
  • try 中抛异常，finally 也抛异常：前者被抑制，后者作为最终抛出（需 Throwable.addSuppressed 关注）。

6. 小结

区分 可恢复（Checked/业务） 与 不可恢复（Error/严重 Bug）；日志记录完整堆栈；API 层用统一异常处理器（如 @ControllerAdvice）转换为用户可读信息，避免向调用方暴露内部细节。
