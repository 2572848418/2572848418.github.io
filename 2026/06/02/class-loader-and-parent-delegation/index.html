类加载机制与双亲委派模型

发表于2026-06-02|更新于2026-06-02
|阅读量:

类加载是 JVM 将 .class 字节码变为可用 Class 对象的过程。理解 加载阶段、ClassLoader 层次、双亲委派 有助于排查 ClassNotFoundException、NoClassDefFoundError 以及 SPI、热部署等机制。

1. 类的生命周期

本文侧重 加载 与 初始化：

  • 加载：通过全限定名获取二进制字节流，生成 Class 对象（方法区/元空间）。
  • 验证：文件格式、元数据、字节码、符号引用合法性。
  • 准备：为类变量分配内存并设 零值（static int 为 0，非代码中的显式赋值）。
  • 解析：符号引用转直接引用。
  • 初始化：执行 <clinit>()，即静态变量赋值与静态块。

主动使用 触发初始化（部分）：

  • new、访问静态字段/方法（非编译期常量）、反射、Class.forName、子类初始化时父类先初始化等。

不会 因访问 编译期常量（static final 基本类型或 String 常量）而初始化类：

2. ClassLoader 层次

加载器 加载范围
Bootstrap（C++ 实现） lib 下核心类，如 java.lang.*
Extension（Platform） lib/ext 或模块扩展
Application classpath、应用 target/classes
自定义 ClassLoader 用户实现，如 Tomcat、Spring Boot Loader

3. 双亲委派模型

流程：类加载请求先交给父加载器；父无法加载时，子加载器才尝试自己加载。

目的：

  1. 避免核心类被应用类覆盖（如自定义 java.lang.String）；
  2. 保证类在 JVM 中 唯一性（同一全限定名由同一加载器加载）。

4. 何时打破双亲委派？

  • SPI（如 JDBC）：核心 API 在 Bootstrap 加载，实现类在 classpath，需 线程上下文类加载器（TCCL） 反向委托。
  • OSGi、Tomcat：不同 Web 应用隔离，同一全限定名可由不同 WebappClassLoader 各加载一份。
  • 热部署、插件化：自定义 loadClass 或 findClass 优先从插件目录加载。

6. 常见问题

异常 常见原因
ClassNotFoundException 类路径无该类、加载器不对、拼写错误
NoClassDefFoundError 编译期存在，运行期依赖缺失或初始化失败
ClassCastException 同一类由不同 ClassLoader 加载，JVM 视为不同类型

7. 小结

类加载将字节码纳入 JVM 管理；双亲委派保护核心类库并维持默认唯一性。SPI、容器与插件场景需要 有意识地打破或调整委派顺序。排查类问题时，应同时检查 classpath、ClassLoader 链与初始化时机。
