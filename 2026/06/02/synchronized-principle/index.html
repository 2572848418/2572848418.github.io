synchronized 原理与锁优化

发表于2026-06-02|更新于2026-06-02
|阅读量:

synchronized 是 Java 最基础的互斥手段，可修饰实例方法、静态方法或代码块。JVM 在 1.6 之后对其做了大量 锁优化（偏向锁、轻量级锁、自旋等），使其在高竞争低时仍有不错性能。

1. 三种使用方式

锁对象：实例方法锁 this；静态方法锁 类.class；代码块锁括号中的对象。任意对象都可作为锁，但应保证多线程使用同一对象。

2. 实现原理概览

synchronized 基于 Monitor（管程） 实现。每个 Java 对象在对象头（Mark Word）中记录锁状态；线程进入同步块时通过 monitorenter / monitorexit 字节码（可递归，计数 +1/-1）与 Monitor 关联。

Monitor 内部有：

  • Owner：当前持有锁的线程；
  • EntryList：阻塞等待锁的线程队列；
  • WaitSet：调用 wait() 后等待的线程。

3. 锁升级过程（JDK 8 及之前常见模型）

无竞争时 JVM 尽量降低开销，典型升级路径：

（JDK 15 起偏向锁默认关闭，JDK 18 逐步移除，新版本中可能直接轻量级/重量级，但理解历史模型仍有参考价值。）

3.1 偏向锁

假设 多数情况下锁总是被同一线程反复获取。Mark Word 记录线程 ID，再次进入时无需 CAS，仅验证 ID。其它线程竞争时撤销偏向，升级为轻量级锁。

3.2 轻量级锁

多线程交替执行同步块、无实际并行竞争时，通过 CAS 将 Mark Word 复制到线程栈的 Lock Record，避免操作系统互斥量开销。

3.3 重量级锁

CAS 自旋多次仍失败，或真正多线程同时竞争，则膨胀为重量级锁，依赖操作系统 Mutex，未获取锁的线程进入阻塞，上下文切换成本高。

4. 与 ReentrantLock 对比

特性 synchronized ReentrantLock
实现 JVM 内置 API（AQS）
释放 自动（块结束/异常） 需 unlock()
可中断 否 lockInterruptibly()
公平锁 非公平 可选公平/非公平
条件变量 单一（wait/notify） 多个 Condition

二者在一般互斥场景性能接近；需要 尝试锁、超时、公平性、多条件队列 时优先 ReentrantLock。

5. 使用建议

  1. 锁粒度尽量小：只包裹必要代码，降低竞争与死锁风险。
  2. 避免锁嵌套：若必须嵌套，统一 加锁顺序 防止死锁。
  3. 不要用 String 常量或包装类型作锁：常量池/缓存导致锁对象被意外共享。
  4. 读多写少 考虑 ReadWriteLock 或并发容器，而非一律 synchronized。

7. 小结

synchronized 通过对象头与 Monitor 实现互斥，JVM 在无竞争或低竞争时通过锁升级减少开销。理解其与 volatile、ReentrantLock 的分工，有助于在并发设计中选对工具。
